# 소규모 셋업 학습 설정 자동 추천기 — 개발 로드맵

> 솔로 · 1학기(~16주) · GPU 작업은 학교 A100 서버, 코드/설계는 협업
> 원칙: **핵심(예측엔진+측정)부터, UI는 나중에. 스코프 좁게 유지. 처음부터 완벽 X, 돌아가는 최소버전(MVP)부터.**

## 스코프 (먼저 못박기)
- **작업**: 파인튜닝 — QLoRA / LoRA / full-FT (추론·프리트레이닝 제외)
- **모델**: 1~2 계열만 (예: Llama-3.1-8B + Qwen2.5-7B)
- **하드웨어**: 1~8 GPU, 단일 노드 (2-GPU까지 병렬화 다룸)
- **프레임워크 타깃**: HuggingFace Accelerate + DeepSpeed(ZeRO)/FSDP + bitsandbytes(4bit)
- **예측 대상**: peak GPU 메모리 / 처리량(tok/s) / 학습시간
- **탐색 대상 설정**: method(full/LoRA/QLoRA), dtype/4bit, batch, grad accumulation, seq len, activation checkpointing, ZeRO stage/FSDP, CPU offload, (2GPU) TP

## 단계별 로드맵

### Phase 0 — 준비 (1주)
- Git 저장소 + 폴더 구조 세팅, 의존성 고정(requirements/conda)
- 학교 A100 서버 접근·환경 확인 (드라이버, CUDA, torch, transformers, peft, accelerate, deepspeed, bitsandbytes 버전 고정)
- 스코프 문서 확정 (위 스코프)

### Phase 1 — 수동으로 학습 1회 완주 (1~2주) ★가장 먼저
- 목적: 도구가 자동화할 "학습 한 번"을 손으로 먼저 돌려보며 knob 체득
- Llama-3.1-8B를 **QLoRA로 A100 1장에서 파인튜닝** (작은 데이터셋, 수백 step)
- 측정법 익히기: `torch.cuda.max_memory_allocated()`, nvidia-smi, tokens/sec, step time
- **일부러 OOM 내보기** (batch 키워서) → 실패 지점 감각 잡기

### Phase 2 — 측정/프로파일링 하네스 (2주) ★핵심 데이터
- 설정을 바꿔가며 **자동으로 짧게(수십~수백 step) 학습 돌리고** peak memory·tok/s·step time을 기록하는 스크립트
- 30~60개 config 데이터포인트 수집 → CSV/DB 저장
- 이 데이터가 뒤의 cost model **보정·검증**의 근거가 됨

### Phase 3 — Cost Model = 예측 엔진 (2~3주) ★프로젝트 심장
- **메모리 예측**: 해석적 공식 구현
  - 파라미터 + gradient + optimizer state(method별: full=Adam 2배, LoRA/QLoRA=어댑터만) + activation(seq·batch·layers·checkpointing 반영) + 4bit 양자화 + 프레임워크 오버헤드
  - 참고: EleutherAI Transformer-Math, Calculon
- Phase 2 실측으로 **상수 보정(fit)** → 예측 vs 실측 오차(MAPE) 측정
- **처리량 예측**: 하드웨어별 효율계수(MFU) 보정 → **점 추정 대신 ±범위**
- 검증: held-out config에서 정확도 리포트 (메모리 MAPE < 5~10% 목표)

### Phase 4 — 탐색 & 추천 로직 (1~2주)
- 설정 공간(수백 조합) → cost model로 각 조합 평가 → **"VRAM에 fit + 처리량 최대"** config 랭킹
- 출력: 추천 config + 예측 수치 + 선택 이유
- (설정 공간이 작아 복잡한 ILP/DP 불필요, 완전탐색으로 충분)

### Phase 5 — Config/스크립트 생성기 (1주)
- 추천 설정을 실행 가능한 **accelerate/deepspeed yaml + launch 명령**으로 생성
- 검증: 생성된 config가 실제로 OOM 없이 돌아가는지 확인

### Phase 6 — 웹 UI (1~2주)
- 입력 폼 → 추천 결과 + 예측 + config 다운로드
- 솔로 친화: **Streamlit 또는 Gradio** (프론트 부담 최소)

### Phase 7 — 평가 & 검증 실험 (2주) ★발표 핵심
- **예측-실측 메모리 MAPE** (헤드라인)
- **OOM 회피율**: naive 기본설정 vs 추천설정
- **GPU 시간 절약**: 예측 후 1회 실행 vs DeepSpeed autotune/삽질
- 여러 (모델·GPU·목표) 시나리오로 벤치

### Phase 8 — 마무리 (1~2주)
- 문서화(README·사용법), 발표자료, 데모 영상, 코드 정리

## 리스크 관리
- **처리량 예측이 어려움** → 범위로 제시, 헤드라인은 메모리 정확도·OOM 회피

## 스코프 결정 이유 (제안서·면담용)
- **파인튜닝만**: 소규모 GPU 사용자의 주 작업이 파인튜닝(QLoRA). 프리트레이닝은 적은 GPU로 거의 안 하고, 추론은 이미 좋은 계산기가 많음 → 빈틈이 파인튜닝. 메모리 구조가 명확해 예측 모델 세우기 좋고, OOM 회피라는 평가 지표가 선명.
- **모델 1~2계열만**: 커버리지보다 **정확도·검증 가능성**. cost model은 모델 구조에 의존 → 계열마다 보정 필요. "정확한 2계열"이 "부정확한 20계열"보다 강함. Llama·Qwen은 표준 구조(디코더+GQA+SwiGLU)라 방법론 확장 가능성 주장 가능. 솔로가 검증(각 30~60런)까지 하려면 2계열이 상한.
- **단일 노드(1~8 GPU)**: 타깃 사용자가 사는 곳. 멀티노드는 통신·토폴로지 모델링이 필요해 난이도 급증(Alpa/Galvatron 영역) → 단일 노드로 좁혀야 완전탐색으로 풀 수 있음.
- **HF+DeepSpeed/FSDP+bitsandbytes 스택**: 소규모 사용자의 실제 표준 스택. Megatron 등 대형·전문가용은 타깃 밖.
- **한 줄 방어**: "커버리지 대신 정확도·검증 가능성을 택했다. 좁혀야 솔로가 한 학기에 '예측이 실제로 맞다'를 증명할 수 있고, 방법론은 확장 가능하다."
