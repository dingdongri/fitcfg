**핵심 메시지 3가지**
1. 세 "고전" 주제(라우팅·speculative decoding 코어·KV 기법)는 2025~2026에 논문·서베이가 쏟아져 **코어는 포화**. 단순 재현/비교로는 novelty 못 만듦.
2. Novelty는 **"아무도 안 건드린 교집합"**에 있음 → (1) 한국어라는 언어 특화, (4) 에이전틱이라는 신흥 워크로드가 가장 유리.
3. **주의**: 순수 라우팅 알고리즘 연구는 GPU가 놀아서 A100을 낭비 → 너희 리소스와 궁합이 안 맞음.

## 1. 한국어/도메인 특화 Speculative Decoding 🥇

### 현황
- **코어 기법은 완전 성숙**: EAGLE-1/2/3, Medusa, self-speculation → vLLM/TensorRT-LLM에 프로덕션 내장.
- **도메인 특화**: 학습 레시피(distillation)까지 정리 완료 → [Training Domain Draft Models (2503.07807)](https://arxiv.org/abs/2503.07807)가 Chinese 포함 best practice 확립. **재현하면 안 됨.**
- **언어 특화는 아직 얇음**: 사실상 [Speculative Decoding Across Languages (2605.30580)](https://arxiv.org/abs/2605.30580) 한 편. 11개 극저자원 언어만 다뤘고 **한국어는 제외**. 표준 speculative decoding이 비영어에서 speedup ≈1.02×로 거의 이득 없음을 보임.

### 열린 문제 (문헌이 명시)
- **언어별 draft 동적 전환** — 2605.30580이 "generation 언어에 따라 draft 모델을 동적으로 바꾸라"고 **말만 하고 안 만듦**.
- **중·고자원 비영어(한국어·일본어 등)는 미조사** — 저자가 직접 blind spot이라 인정.
- **context-establishment 병목** — 초반 토큰이 33% vs 후반 24%로 훨씬 많이 reject ([RyeCatcher 분석](https://huggingface.co/RyeCatcher/speculative-decoding-cross-domain-analysis)).

### 이 팀을 위한 novelty 각도 (순위)
1. **한국어 특화 draft 모델 + 한국어 speculative decoding acceptance-rate 벤치마크** — EXAONE-7.8B 또는 HyperCLOVA X SEED 타깃에 EAGLE-3 draft 학습. 한국어 첫 체계적 speedup 연구. **한국어 형태소/토큰 분절 특성**이 acceptance에 주는 영향을 분석하면 확실한 차별점.
2. **한-영 코드스위칭 인지 동적 draft 전환** — 한국어 실텍스트는 영어 기술용어·코드 혼용이 많음. 생성 스팬의 언어에 따라 한국어/영어 draft를 전환하는 경량 라우터. 2605.30580이 이름만 붙인 열린 문제를 실제 구현.

### ⚠️ 피할 것
- 일반 도메인 draft 학습/distillation (2503.07807이 이미 함)
- 일반 목적 동적 draft length/tree RL ([Learning to Draft 2603.01639](https://arxiv.org/html/2603.01639v1)이 가져감)
- acceptance-rate loss 함수 (LK Losses 2602.23881)
- EAGLE-3를 이기는 새 draft-head 아키텍처 (1학기 2인으로는 무리)

### 리소스 궁합: **최적**
7.8B 타깃(bf16 ~16GB) + 작은 draft → A100 80GB 1장에서 학습·서빙 여유. EAGLE 학습 수 시간~수일. 데모: 한국어 챗 side-by-side로 tokens/sec·acceptance 실시간 표시.

## 2. LLM 라우팅 / 캐스케이드 🥉

### 현황 — 텍스트 라우팅은 포화 심함
- FrugalGPT(2023) → RouteLLM(2024)로 대중화. 2026년 서베이 [2603.04445](https://arxiv.org/abs/2603.04445)가 8개+ 방법군으로 이미 분류.
- **충격적 사실**: 2026 벤치마크 논문들이 "정교한 라우터가 자명한 baseline과 거의 구분 안 됨"을 반복 보고 ([LLMRouterBench 2601.07206](https://arxiv.org/html/2601.07206v1), [RouterEval 2503.10657](https://arxiv.org/abs/2503.10657)). 저수익 과일은 다 따감.

### 열린 문제 (서베이가 3개 명시)
- (a) retraining-free 일반화 → **이미 [Universal Model Routing 2502.08773](https://arxiv.org/abs/2502.08773), [Arch-Router 2506.16655](https://arxiv.org/abs/2506.16655)가 상당 부분 해결**. 거의 포화.
- (b) 다단계 캐스케이드 → 2단계는 [Cluster-Route-Escalate 2606.27457](https://arxiv.org/abs/2606.27457)이 함. 3단계+가 남음.
- (c) **멀티모달 라우팅 → 가장 덜 파임.** [LatentRouter 2605.11301](https://arxiv.org/html/2605.11301)만 겨우 시작, 멀티모달 *캐스케이드*는 미개척.

### 이 팀을 위한 novelty 각도
1. **멀티모달(VLM) 캐스케이드 + 불확실성 기반 escalation** — 저렴한 VLM(Qwen2.5-VL-7B)이 먼저 답하고, confidence로 강한 VLM(72B AWQ)에 escalate. 시각 서브스킬(OCR/차트/공간추론)별 라우팅. → **멀티모달 캐스케이드는 아직 없음.**
2. **진짜 GPU 비용을 재는 시스템 게이트웨이** — 대부분 논문은 API $/token(추상)으로 평가. 실제 latency/throughput/KV압력/에너지를 측정하는 라우터. 서베이가 "quality·cost·latency 통합 최적화 없음"을 지적.

### ⚠️ 피할 것 + 치명적 경고
- 선호데이터 기반 강/약 텍스트 라우터(=RouteLLM), 또 다른 라우팅 벤치마크 → 완전 포화.
- **GPU가 필요없을 수 있음**: RouterBench류는 precomputed 행렬 제공 → 라우팅 알고리즘 연구는 노트북으로 가능. **A100이 놀면 너희 리소스와 미스매치.** 멀티모달 self-hosting(#1)이나 실서빙 측정(#2)일 때만 GPU가 정당화됨.

## 3. 긴 컨텍스트 KV Cache 최적화 🥈 (시스템 강점 팀에 적합)

### 현황 — 기법은 초포화, 시스템 통합은 열림
- 최근 12개월에 서베이만 4편. quantization(KIVI, KVQuant…), eviction(H2O, SnapKV, PyramidKV…), low-rank(Palu, ShadowKV…)은 **수십 편 → 초포화**.
- 하지만 [ACL 2026 서베이 (2607.08057)](https://arxiv.org/abs/2607.08057)가 명시: 개별 기법은 성숙, **결합·스케줄링·벤치마킹·tail latency/SLO는 미개발**. → **novelty는 시스템 "글루"에 있음, 새 압축 수학이 아님.**

### 열린 문제 (서베이 6개 챌린지)
- C1 SLO/tail 제어 + preemption 의미론 부재
- C5 **co-optimization** — eviction·offload·prefetch를 따로 최적화함(같이 해야 함)
- C6 통일 벤치마크 부재
- tiered/cross-tier eviction 정책 부족 ([memory hierarchy 서베이 2607.02574](https://arxiv.org/html/2607.02574))

### 이 팀을 위한 novelty 각도 (시스템 백그라운드 활용)
1. **적응형 KV offload+prefetch 정책 (vLLM/LMCache 플러그인, SSD 티어)** — GPU→CPU→SSD 3티어를 런타임 신호(attention-mass, reuse recency, phase)로 **공동 결정**. 서베이 C5 정조준.
2. **SLO/tail 인지 KV 스케줄러 + preemption** — [이론만 있는 2502.07115](https://arxiv.org/abs/2502.07115)을 실제 vLLM 스케줄러 플러그인으로 구현. C1 정조준.
3. **KV 기법 통합 벤치마크 하네스** — eviction×quant×offload 조합의 상호작용 측정. C6. (완성도 안전판)

### ⚠️ 피할 것
새 eviction 점수, 새 quantization, 새 low-rank, 바닐라 CPU offload/prefix caching → 전부 포화. 엔진을 처음부터 만들지 말 것(vLLM/LMCache 위에 플러그인).

### 리소스 궁합: 좋음 (단 시스템 쪽에 머물 것)
A100 1장이면 7~14B 장문 서빙 충분. 난이도 리스크는 "새 압축 수학"으로 새면 큼 → 스케줄링/offload 정책으로 좁히면 1학기 적정.

## 4. 에이전틱(Agent) 워크로드 서빙 🥇

### 현황 — 신흥, 1차 물결 완료 / 2차 물결 열림 (고전 서빙보다 여유 있음)
- **이미 된 것(1차)**: 프로그램 레벨 스케줄링([Autellix 2502.13965](https://arxiv.org/abs/2502.13965)), 툴콜 넘어 KV 유지([Continuum 2511.02230](https://arxiv.org/abs/2511.02230), [TokenCake 2510.18586](https://arxiv.org/abs/2510.18586)), 알려진 워크플로 그래프 기반 KV eviction([KVFlow 2507.07400](https://arxiv.org/abs/2507.07400)), 의존성 노출 추상화([Parrot OSDI'24](https://arxiv.org/abs/2405.19888)).
- **열린 것(2차)**: 논문마다 같은 걸 future work로 미룸 → **동적/온라인 공개 워크플로 그래프, 학습 기반 구조 추론, 예측 실패 시 robustness, cross-session 캐시 공유, 단일GPU 결과의 분산화**.

### 이 팀을 위한 novelty 각도 (순위)
1. **동적 agent 그래프를 위한 robustness-first KV 관리** — 학습 기반 전환 예측([CacheScout 2608.14624](https://arxiv.org/abs/2608.14624))이 포기한 부분: **예측이 안 될 때의 우아한 degradation.** 예측 confidence를 온라인 측정해 learned score와 LRU를 엔트로피 비례로 혼합 → "구조 있으면 최선 예측기만큼, 없으면 LRU보다 절대 안 나쁨"이라는 명확한 주장.
2. **프레임워크 네이티브 cache-aware 미들웨어 (엔진 무수정)** — 대부분 엔진을 고침. 대신 LangGraph/AutoGen 콜백에서 live DAG 복원 + prefix-cache 인지 라우팅을 **무수정 vLLM/SGLang 앞단 미들웨어**로. "엔진 접근 없이 얼마나 이득을 살리나?" → 연구 포인트 + 강한 데모.
3. **에이전틱 서빙 효율 벤치마크 하네스** — 표준 서빙 벤치가 없음(SWE-bench/τ-bench는 정확도 측정). 실제 agent 트레이스 replay로 서빙 지표 측정. (완성도 안전판, scoop 위험 낮음)

### ⚠️ 피할 것
프로그램 레벨 스케줄링(Autellix), TTL/pinning(Continuum·TokenCake), 알려진 그래프 KV eviction(KVFlow), 분산 KV풀(Mooncake, 대형 프로덕션과 경쟁 X), 이종 클러스터(HexAGenT, 멀티노드 필요).

### 리소스 궁합: 최적
영향력 있는 결과 대부분(TokenCake·Continuum·KVFlow·CacheScout)이 **단일 GPU + 7~8B**로 나옴. A100 1장 충분, 2장이면 baseline vs ours 동시. **엔진 포크 금지, SGLang/vLLM 위 shim으로.** 게시된 개선폭 1.5~8×라 일부만 잡아도 명확한 결과.

## 5. 최종 권고

### 두 개의 강력 후보
- **주제 1 (한국어 Speculative Decoding)** — Novelty가 "한국어"라는 자연스러운 white space에서 나오고, 학습+서빙 둘 다 있어 ML+시스템 균형. 데모 명확. **한국인 팀의 구조적 강점.**
- **주제 4 (에이전틱 서빙)** — 신흥 영역이라 고전 서빙보다 novelty 여지 큼. 시스템 백그라운드 직접 활용. 데모 임팩트 최고(1.5~8× 개선폭). 단 필드가 빠르게 움직여 **주제를 좁게 못박고 빨리 시작**해야 함.

### 팀 성향별 선택 가이드
- **ML 학습 경험을 쌓고 싶다 / 한국어 강점을 살리고 싶다** → **주제 1**
- **순수 시스템·스케줄링이 재밌다 / OS 강점을 살리고 싶다** → **주제 4** (또는 주제 3)
- **안정성 최우선(완성 보장)** → 주제 4의 #3(벤치마크 하네스) 먼저 만들고 #1/#2 얹기, 또는 주제 3의 #3

### 공통 리스크 관리
1. **2026년(2601~2608) arxiv는 매우 빠름** — 주제 확정 직전, 가장 가까운 경쟁 논문(주제1: 2605.30580 / 주제4: CacheScout 2608.14624)이 그 사이 확장판을 냈는지 재확인.
2. **엔진을 처음부터 만들지 말 것** — 전부 vLLM/SGLang/LMCache/EAGLE 위에 얹기.
3. **벤치마크/하네스를 먼저** — 완성 안전판이자 novelty 실패 시 fallback 딜리버러블.

## 부록 A — 주제1(한국어 Spec Decoding) Novelty 적대적 검증 결과

> 2026-09-11 추가. "이미 누가 했나"를 힘껏 찾은 결과. **결론: naive 버전은 선점됨. 좁은 틈 2개만 생존.**

### ❌ 이미 선점된 것 (헤드라인으로 쓰면 안 됨)
- **[2406.16758](https://arxiv.org/abs/2406.16758) (KAIST/KT, EMNLP 2024)** — 언어별 특화 draft + 언어별 acceptance/speedup 벤치마크(일·중·독·불·러). **한국어만 제외, 저자가 한국 연구진.** 공개 벤치마크 [Multilingual-SpecBench](https://github.com/Kthyeon/Multilingual-SpecBench)까지 존재. → "한국어 draft + 벤치마크"는 N+1 증분.
- **[2604.05417](https://arxiv.org/abs/2604.05417) (MetaSD, ACL 2026, 같은 랩)** — 동적 멀티 draft 전환을 밴딧으로 이미 구현. → "언어별 동적 전환" 각도 거의 닫힘.
- **NAVER CLOVA (2025.08)** — HyperCLOVA X에 spec decoding 실서비스 적용(방법 비공개). "한국어 LLM + spec decoding"은 이미 산업 현실.
- **[2510.02128](https://arxiv.org/html/2510.02128v1)** — 언어별 acceptance 격차(공정성) 이미 측정.

### ✅ 생존한 틈 2개
1. **한-영 코드스위칭 인지 spec decoding** — 문장 내 한·영 혼용에서 draft 전환/acceptance 붕괴. 아무도 안 함. 2406.16758이 "mixed-language 미해결"로 명시. 한국어가 필연적으로 부각.
2. **형태소 경계 acceptance 분해 + 분절도(fertility)→acceptance 정량 법칙 + 토크나이저 ablation** — 교착어가 어디서 draft를 무너뜨리는가의 메커니즘 분석. 미개척. 단 [2604.14682](https://arxiv.org/html/2604.14682)이 "도메인별 acceptance 분해"라는 동일 형태의 분석을 이미 함 → 창이 빨리 닫힐 수 있음.

### 솔로 진행 관점 우려
- 남은 틈이 좁고 최근접 경쟁자가 활발한 한국 랩(KAIST) → 솔로 리스크 높음.
- 두 각도 다 분석 밀도 높음 → 논문성엔 맞으나 "실사용 데모" 축은 약함.
- 혼자서 draft 학습 + 서빙 + 분석 전부 부담.

### 실무 결론
주제1로 가려면 **반드시 코드스위칭 또는 형태소-메커니즘으로 좁혀야** 하고, 단순 "한국어 draft 학습"은 금지. 이 좁힘이 부담스러우면 **주제4(에이전틱 서빙)가 솔로+시스템 강점엔 더 안전**.

## 부록 B — 주제4도 검증: 세 각도 전부 선점됨

- **각도 A (동적 그래프 robust KV)**: [CacheScout(2608.14624)](https://arxiv.org/abs/2608.14624)가 온라인 confidence+LRU 우아한 후퇴를 거의 그대로 구현, [PBKV(2605.06472)](https://arxiv.org/html/2605.06472v1)는 Lipschitz 증명까지. → 남은 건 좁은 이론 조각.
- **각도 B (무수정 미들웨어)**: prefix-cache-aware 라우팅은 이미 제품 기능(vLLM production-stack, SGLang Router, llm-d, Dynamo, Ray). [CacheSage(2605.27744)](https://arxiv.org/abs/2605.27744)가 외부 런타임 레이어를 논문화. → 선점.
- **각도 C (에이전틱 벤치마크)**: [XPerf(2608.20370)](https://arxiv.org/abs/2608.20370)가 거의 동일, 오픈소스화 중. MLPerf 공식 벤치 제작 중. → 선점.

**메타 교훈**: 서베이가 "열려있다"는 뜨거운 영역일수록 수십 랩이 동시에 파고 있어, 솔로 학부생이 "프론티어 novelty"를 겨냥하면 몇 달 전 프리프린트에 거의 항상 선점당함.

## 부록 C — 최종 방향 결정: "학습 설정 자동 추천기" (도구/서비스)

> 연구 novelty가 아니라 **"있으면 유용한데 아직 없는 AI 시스템 도구"**를 만드는 방향으로 전환. 평가 = 완성도·실사용·설계. 솔로 소유 가능, scoop 리스크 낮음. 사용자의 3D parallelism search 경험 직결.

### 확인된 빈틈 (지형 조사 결과)
- 연구 시스템(Alpa/Galvatron/nnScaler/Metis) = 대형 클러스터용 + 유지보수 안 됨 + 비전문가 못 씀.
- 실용 계산기(HF estimate-memory/gpu_poor/DeepSpeed autotune/NeMo autoconfig) = 메모리만/추론용, 또는 실제 job 다회 실행(느림/비쌈), NeMo는 최소 16 GPU.
- **아무도 "1~8 GPU 단일 노드 소규모 셋업 + 실행 전 예측 + 최적 config 탐색 + 실행가능 config 생성"을 안 함.** ← 여기가 프로젝트 자리.

### 프로젝트 정의
**소규모 셋업 학습 사전점검 어드바이저**: `(모델 + GPU 구성 + 목표 + seq len)` → ① 실행 전 메모리·처리량·시간 예측 → ② config 공간(FSDP/ZeRO 단계·micro-batch·grad accum·activation checkpointing·offload·2-GPU TP) 탐색·추천 → ③ 바로 돌릴 Accelerate/DeepSpeed config+명령 생성.

**핵심 기여**: 예측 vs 실측 정확도를 A100에서 실측·검증(기존 계산기가 절대 안 하는 것).

**함정**: 처리량 예측은 어려움 → ±band로, 헤드라인은 메모리 정확도+OOM 회피+GPU 시간 절약. 3D parallelism 경험은 클러스터 재발명(함정) 말고 소규모 usability에 겨냥.

**데모/평가**: 예측-실측 MAPE(<5~10%), OOM 회피 벤치, GPU 시간 절약(예측 후 1회 vs trial-and-error).

**참고 자산(재사용)**: EleutherAI Transformer-Math 공식, Calculon cost model, LLMem, gpu_poor, HF estimate-memory. **비교/베이스라인**: DeepSpeed autotuning, NeMo Auto Configurator.
